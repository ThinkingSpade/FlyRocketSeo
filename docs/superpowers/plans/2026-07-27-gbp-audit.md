# Google Business Profile Audit Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Score the Google Business Profile the app already caches — completeness, categories, description, imagery, reviews and owner responsiveness — and turn the gaps into ranked, specific fixes.

**Architecture:** A pure scoring module in the shape of `src/client/features/insights/verdicts/*`, fed entirely by data already fetched by `LocalSeoService`. No new metered call. Rendered on the Local SEO tab using the existing `NextStepsCard` and `InsightTile` primitives.

**Why this is cheap:** `getCachedBusinessContext` already returns the full profile (`title`, `category`, `additionalCategories`, `description`, `logo`, `mainImage`, `phone`, `url`, `isClaimed`, `rating`, `reviewsCount`) and the reviews payload already carries `ownerAnswer` per review. The audit is arithmetic over data on hand.

**Origin:** BrightLocal parity — their GBP Audit is the feature we most cheaply match, because we already hold the inputs. See the memory note `flyrocketseo-brightlocal-parity`.

## Global Constraints

- **`pnpm ci:check`** = `prettier --check . && knip && tsc --noEmit && oxlint . --type-aware`. All four must pass.
- **Vitest collects only `src/**/\*.test.ts`** (`.ts`, not `.tsx`), `environment: "node"`. The scoring module is pure and MUST be tested. React components get no tests; there is no React test infrastructure and adding it is out of scope.
- **oxlint `no-unsafe-type-assertion`** — never `as`-narrow an `unknown`; use a type-predicate guard. `max-lines-per-function` is 320 and applies to `describe` blocks; split into sibling describes rather than disabling.
- **knip fails on unused exports.** Test-only exports are tolerated.
- **No new metered spend.** The audit must read only what `LocalSeoService` has already fetched and cached. If a signal would require a new provider call, leave it out and say so.
- **Never invent a finding.** Every check must be derivable from a field actually present. A field being `null` means "we don't know", which is NOT the same as "the business hasn't set it" — see Task 1.
- **Comments explain WHY, not what.** Package manager is pnpm.

## Task 1: The scoring model

**Files:**

- Create: `src/client/features/local-seo/gbpAudit.ts`
- Test: `src/client/features/local-seo/gbpAudit.test.ts`

**Interfaces:**

- Consumes: the `BusinessProfile` shape from `LocalSeoService` (title, category, additionalCategories, address, city, region, phone, url, domain, rating, reviewsCount, isClaimed, description, logo, mainImage, found).
- Produces: `buildGbpAudit(input): GbpAudit` where

```ts
export type GbpCheckStatus = "pass" | "warn" | "fail" | "unknown";

export type GbpCheck = {
  key: string;
  label: string;
  status: GbpCheckStatus;
  /** What the data actually says. Shown under the label. */
  detail: string;
  /** Imperative fix, only when status is warn or fail. */
  fix: string | null;
  /** Ranked by this, descending. */
  weight: number;
};

export type GbpAudit = {
  /** 0-100, or null when too little is known to score honestly. */
  score: number | null;
  checks: GbpCheck[];
};
```

### THE RULE THAT MATTERS MOST

A `null` field means **we do not know**, not "the business left it blank". DataForSEO returning `description: null` can mean the profile has no description OR that the field was not returned. Conflating those would tell a user to "add a description" they already wrote.

So: an absent field yields `status: "unknown"` with a `detail` that says the data is unavailable, `fix: null`, and it is EXCLUDED from the score denominator. Only checks we can actually evaluate count toward the score. If fewer than half the checks are evaluable, `score` is `null` and the UI says so rather than showing a misleadingly precise number.

`found: false` (no profile at all) returns `score: null` and a single check explaining that.

Run: `sed -n '14,40p' src/server/features/local-seo/services/LocalSeoService.ts`
Run: `cat src/client/features/insights/verdicts/backlinks.ts`

Match the verdict modules' structure, comment voice, and use of named threshold constants.

- [ ] **Step 2: Write the failing tests**

Cover, at minimum:

- `found: false` ⇒ `score: null`, exactly one check explaining no profile was found
- an unclaimed profile (`isClaimed: false`) ⇒ a `fail` check with the highest weight of any check, because an unclaimed profile blocks every other improvement
- `isClaimed: null` ⇒ `unknown`, NOT `fail`, and excluded from the score
- no primary `category` ⇒ `fail`; a primary category present with an empty `additionalCategories` ⇒ `warn` (Google allows up to 9 and unused slots are lost reach)
- `description: null` ⇒ `unknown` with `fix: null`
- `description: ""` ⇒ `fail` (genuinely empty, distinct from unknown)
- a description under 100 characters ⇒ `warn`; a healthy one ⇒ `pass`
- missing `logo` ⇒ `warn`; missing `mainImage` ⇒ `warn`
- missing `phone` ⇒ `fail`
- `url: null` ⇒ `unknown`; a `url` whose host does not match the project's domain ⇒ `warn` naming both hosts
- `reviewsCount: 0` ⇒ `fail`; a low count ⇒ `warn`; healthy ⇒ `pass`
- `rating` below a named threshold ⇒ `warn`
- **score arithmetic**: a profile where every evaluable check passes ⇒ `100`; a known mix ⇒ an exact expected number (compute it by hand in the test, do not assert a range)
- **score excludes unknowns**: two inputs identical except that one has extra `null` fields must produce the SAME score, proving unknowns do not drag it down
- checks are returned sorted by weight descending

## Task 2: Owner response rate

**Files:**

- Modify: `src/client/features/local-seo/gbpAudit.ts` + its test

**Interfaces:**

- Produces: `buildGbpAudit` gains an optional `reviews` input: `Array<{ ownerAnswer: string | null }>`.

Owner responsiveness is a real profile-quality signal and the reviews payload already carries `ownerAnswer` per review, so it costs nothing extra.

- [ ] **Step 1: Write the failing tests**

- no reviews array supplied ⇒ an `unknown` check, excluded from the score (do not assume zero responses)
- an empty reviews array ⇒ `unknown`, not `fail` — no reviews means nothing to respond to
- 0% responded across several reviews ⇒ `fail`, detail naming the count
- a low rate ⇒ `warn` with the exact percentage
- a high rate ⇒ `pass`
- the percentage in `detail` is exact for a case you compute by hand

- [ ] **Step 2: Build the card**

- A headline score tile. When `score` is `null`, show an em dash and a hint saying why — never a fabricated number.
- The checks as a list, ranked, each showing label, status, detail and (when present) the fix.
- Status colour follows the existing tone convention: `fail` → error, `warn` → warning, `pass` → success, `unknown` → neutral/muted.
- **`unknown` checks render last and visually quieter.** They are not problems; presenting them alongside failures would inflate the apparent severity.
- Render only when a profile has actually been looked up. Do not render an empty audit shell.
